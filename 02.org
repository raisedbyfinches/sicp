** Rational data types

Haskell actually has a data type where a rational number is represented as a pair (numerator and denominator) and both are tracked throughout its lifetime. This is ~Rational~ (though that's just a synonym for ~Ratio Integer~. They are stored in reduced form so along the way it has to be divided by its GCD. They make the denominator always positive so that the sign of the number is carried in the numerator.

This enables us to represent fractions without rounding errors (looking at you floating-point numbers). For symbolic computations and in certain domains this is useful because of the higher precision. Though the operations can be slower because of needing to calculate the GCD and when the size of the numerator and denominator grow significantly this can use a lot more memory.

So its not *completely* insane to build data types in this way.

** Exercise 1
Define a better version of ~make-rat~ that handles both positive and negative arguments. ~make-rat~ should normalize the sign so that if the rational number is positive, both the numerator and denominator are positive, and if the rational number is negative, only the numerator is negative.

#+begin_src scheme
;; Define a constructor for rational numbers
(define (make-rat n d)
  (let* ((g (gcd n d))              ; Compute GCD
         (numer (/ n g))            ; Reduce
         (denom (/ d g)))           ; Reduce
    (if (< denom 0)                 ; Ensure denominator is positive
        (cons (- numer) (- denom))  ; Flip signs if denominator is negative
        (cons numer denom))))       ; Otherwise, return as is
#+end_src

#+begin_src scheme
;; Constructor for points
(define (make-point x y)
  (cons x y))

;; Selectors for points
(define (x-point p) (car p))
(define (y-point p) (cdr p))

;; Constructor for segments
(define (make-segment start end)
  (cons start end))

;; Selectors for segments
(define (start-segment s) (car s))
(define (end-segment s) (cdr s))

(define (midpoint-segment s)
  (let ((start (start-segment s))
        (end (end-segment s)))
    (make-point
     (/ (+ (x-point start) (x-point end)) 2)
     (/ (+ (y-point start) (y-point end)) 2))))

* Extended exercise: interval arithmetic

This has so much pre-amble. Essentially using an interval to capture a range of possible values. There's plenty of use cases of such a thing where the exact values aren't known but the bounds of uncertainty can be established.

Intervals:
 - represented by a lower and upper bound
 - extend arithmetic operations to work with intervals, producing new intervals encompassing all possible results of the operation

The key idea is that by working with intervals, we can carry uncertainty through the computations. This ensures results remain valid even with imprecise inputs.

** Exercise 8

*** Solution
To compute the difference between two intervals $A = [a, a']$ and $B=[b, b']$ the smallest possible is the minimum of all of the differences and the upper bound is the maximum of all of the differences. So the subtraction of intervals could look like:

#+begin_src scheme
(define (sub-interval x y)
  (let ((a (- (lower-bound x) (upper-bound y)))
        (b (- (upper-bound x) (lower-bound y)))
        (c (- (lower-bound x) (lower-bound y)))
        (d (- (upper-bound x) (upper-bound y))))
    (make-interval (min a b c d)
                   (max a b c d))))
#+end_src

** Exercise 9

The width of an interval is half of the difference between its upper and lower bounds. The width is a measure of the uncertainty of the number specified by the interval. For some arithmetic operations the width of the result of combining two intervals is a function only of the widths of the argument intervals, whereas for others the width of the combination is not a function of the widths of the argument intervals. Show that the width of the sum (or difference) of two intervals is a function only of the widths of the intervals being added (or subtracted). Give examples to show that this is not true for multiplication or division.

*** Solution

The definition of the width from the above is:

#+begin_src scheme
  (define (width interval)
    (/ (- (upper-bound interval) (lower-bound interval)) 2))
#+end_src


1. When adding two intervals:
   - Interval 1: $[a_1, b_1]$
   - Interval 2: $[a_2, b_2]$
   - Resulting interval: $[a_1 + a_2, b_1 + b_2]$
   - Width of the resulting interval:
             \begin{aligned}
     width &= \frac{(b1 + b2) - (a1 + a2)}{2} \\
           &= \frac{(b1 - a1) + (b2 - a2)}{2} \\
           &= w1 + w2
     \end{aligned}
   - Thus, the width of the sum is a function only of the widths of the input intervals.

2. When subtracting two intervals:
   - Interval 1: $[a_1, b_1]$
   - Interval 2: $[a_2, b_2]$
   - Resulting interval: $[min(a_1 - b_2, a_1 - a_2, b_1 - b_2, b_1 - a_2), max(a_1 - b_2, a_1 - a_2, b_1 - b_2, b_1 - a_2)]$
   - Width of the resulting interval:
     \begin{aligned}
     width &= \frac{1}{2}max(a_1 - b_2, a_1 - a_2, b_1 - b_2, b_1 - a_2) \\
           &- \frac{1}{2}min(a_1 - b_2, a_1 - a_2, b_1 - b_2, b_1 - a_2)
     \end{aligned}
   - However, after simplification, it can be shown that the width of the resulting interval is still ~w1 + w2~, because the subtraction operation does not introduce additional dependencies beyond the bounds of the input intervals.

3. When multiplying two intervals:
   - Interval 1: $[a_1, b_1]$
   - Interval 2: $[a_2, b_2]$
   - Resulting interval: $[min(a_1*a_2, a_1*b_2, b_1*a_2, b_1*b_2), max(a_1*a_2, a_1*b_2, b_1*a_2, b_1*b_2)]$
   - The width of the resulting interval depends on the specific values of $a_1, b_1, a_2, b_2$, not just their widths. For example:
     + Interval 1: $[1, 2]$ (width = 0.5)
     + Interval 2: $[3, 4]$ (width = 0.5)
     + Resulting interval: $[3, 8]$ (width = 2.5, which is not $0.5 + 0.5$).

4. When dividing two intervals:
   - Interval 1: $[a_1, b_1]$
   - Interval 2: $[a_2, b_2]$ (assuming $0 ∉ [a_2, b_2]$ to avoid division by zero)
   - Resulting interval: $[min(a_1/a_2, a_1/b_2, b_1/a_2, b_1/b_2), max(a_1/a_2, a_1/b_2, b_1/a_2, b_1/b_2)]$
   - The width of the resulting interval depends on the specific values of $a_1, b_1, a_2, b_2$, not just their widths. For example:
     + Interval 1: $[1, 2]$ (width = 0.5)
     + Interval 2: $[3, 4]$ (width = 0.5)
     + Resulting interval: $[1/4, 2/3]$ (width ≠ $0.5 + 0.5$).

** Exercise 11
In passing, Ben also cryptically comments: "By testing the signs of the endpoints of the intervals, it is possible to break mul-interval into nine cases, only one of which requires more than two multiplications." Rewrite this procedure using Ben’s suggestion.

*** Solution
#+begin_src scheme
(define (mul-interval x y)
  (let ((lx (lower-bound x))
        (ux (upper-bound x))
        (ly (lower-bound y))
        (uy (upper-bound y)))
    (cond
      ;; Case 1: Both intervals are entirely positive
      ((and (>= lx 0) (>= ly 0))
       (make-interval (* lx ly) (* ux uy)))

      ;; Case 2: x is positive, y spans zero
      ((and (>= lx 0) (<= ly 0 uy))
       (make-interval (* ux ly) (* ux uy)))

      ;; Case 3: x is positive, y is entirely negative
      ((and (>= lx 0) (<= uy 0))
       (make-interval (* ux ly) (* lx uy)))

      ;; Case 4: x spans zero, y is positive
      ((and (<= lx 0 ux) (>= ly 0))
       (make-interval (* lx uy) (* ux uy)))

      ;; Case 5: Both intervals span zero
      ((and (<= lx 0 ux) (<= ly 0 uy))
       (make-interval (min (* lx uy) (* ux ly))
                      (max (* lx ly) (* ux uy))))

      ;; Case 6: x spans zero, y is negative
      ((and (<= lx 0 ux) (<= uy 0))
       (make-interval (* ux ly) (* lx ly)))

      ;; Case 7: x is entirely negative, y is positive
      ((and (<= ux 0) (>= ly 0))
       (make-interval (* lx uy) (* ux ly)))

      ;; Case 8: x is entirely negative, y spans zero
      ((and (<= ux 0) (<= ly 0 uy))
       (make-interval (* lx uy) (* lx ly)))

      ;; Case 9: Both intervals are entirely negative
      ((and (<= ux 0) (<= uy 0))
       (make-interval (* ux uy) (* lx ly))))))
#+end_src

** Exercise 16
Explain, in general, why equivalent algebraic expressions may lead to different answers. Can you devise an interval-arithmetic package that does not have this shortcoming, or is this task impossible? (Warning: This problem is very difficult.)

*** Solution
I think this is far too difficult for civil servants. So let's think about *why* its so hard.

The fundamental issue is that of _identity_ in interval arithmetic and is even a named problem. You can read more about it if you search for the *Dependency Problem*.

Identity in regular arithmetic is trivial. For example, if $x=5$ then every instance of $x$ is exactly 5. This means that, unambiguously, $x*x = 5*5 = 25$.

Now, taking this into the realm of interval arithmetic. If two $x$'s existed the value of one $x$ is not necessarily the same as another. For example, let us assume that is the interval $[3,10]$. Now $\frac{x}{x}$ could be $1$. That is, if it meant $\frac{3}{3}$ or $\frac{8}{8}$. However, its possible that it could mean $\frac{4}{9}$ or something else. These values are within the specified range and it is theoretically possible. The problem is, we don’t know what the values are.

There is no obvious way, mathematically, to introduce identity into interval arithmetic.

Louis Reasoner tries to rewrite the first =square-list= procedure of Exercise 2.21 so that it evolves an iterative process:

#+begin_src scheme
(define (square-list items)

Unfortunately, defining =square-list= this way produces the answer list in the reverse order of the one desired. Louis tries to fix his bug by interchanging the arguments to =cons=:

#+begin_src scheme
(define (square-list items)
  (define (iter things answer)
    (if (null? things)
        answer
        (iter (cdr things)
              (cons answer
                    (square (car things))))))
  (iter items '()))
#+end_src

*** Solution
The first version produces a reversed list because =cons= prepends each new squared element to the front of the accumulator. Since elements are processed left to right, each element ends up before all previously processed elements, yielding a reversed result.

The second version doesn't fix the problem because swapping the arguments to =cons= doesn't change the order of processing — it just builds an improper nested list structure rather than a flat list. Instead of =(cons new-element list)=, Louis writes =(cons list new-element)=, which places the growing list as the =car= and the new element as the =cdr=, producing a structure like =(((() . 1) . 4) . 9)= rather than =(1 4 9)=.

The correct iterative approach is to either reverse the result at the end, or build the list in reverse using =cons= and then apply =reverse=:

#+begin_src scheme
(define (square-list items)
  (define (iter things answer)
    (if (null? things)

Two lists are said to be =equal?= if they contain equal elements arranged in the same order. For example:

To be more precise, we can define =equal?= recursively in terms of the basic =eq?= equality of symbols by saying that =a= and =b= are =equal?= if they are both symbols and the symbols are =eq?=, or if they are both lists such that =(car a)= is =equal?= to =(car b)= and =(cdr a)= is =equal?= to =(cdr b)=. *** Solution

        ((or  (null? a) (null? b)) #f)

** Exercise 55
Eva Lu Ator types to the interpreter the expression ='(a b)= and is surprised when the interpreter prints back =(quote (a b))= rather than =(a b)=. Explain.

*** Solution
The single-quote character ='= is reader syntax — a shorthand that the Lisp reader expands before the interpreter ever sees it. Specifically, ='x= is expanded to =(quote x)= during the read phase.

So when Eva types ='(a b)=, the reader first expands the leading ='= and produces =(quote (a b))=. But now the entire expression is =(quote (a b))=, which itself begins with a ='=! In other words, she has effectively typed =''(a b)=, which the reader expands in two steps:

#+begin_src
''(a b)
→ '(quote (a b))
→ (quote (quote (a b)))
#+end_src

When the interpreter evaluates =(quote (quote (a b)))=, it returns the unevaluated form =(quote (a b))=, which the printer displays as =(quote (a b))=. If Eva had typed just =(a b)= or ='(a b)= without the extra quote, she would have gotten the expected result.

(define (augend s)

*** Solution
#+begin_src scheme
; Part a — fully parenthesized infix
(define (sum? exp)
  (and (pair? exp) (eq? (cadr exp) '+)))

(define (addend exp) (car exp))
(define (augend exp) (caddr exp))

(define (make-sum a b)
  (cond ((=number? a 0) b)
        ((=number? b 0) a)
        ((and (number? a) (number? b)) (+ a b))
        (else (list a '+ b))))

(define (product? exp)
  (and (pair? exp) (eq? (cadr exp) '*)))

(define (multiplier exp) (car exp))
(define (multiplicand exp) (caddr exp))

(define (make-product a b)
  (cond ((or (=number? a 0) (=number? b 0)) 0)
        ((=number? a 1) b)
        ((=number? b 1) a)
        ((and (number? a) (number? b)) (* a b))
        (else (list a '* b))))

; Part b — standard infix with precedence (+ binds looser than *)
; The key idea: a sum is any expression whose top-level operator is +,
; where "top-level" means not nested inside a * subexpression. We find
; the rightmost + that is not inside parentheses.

(define (find-rightmost-op op expr)
  ; Returns the index of the rightmost occurrence of op at the top level,
  ; or #f if not found. We scan right-to-left.
  (define (scan lst depth idx best)
    (cond ((null? lst) best)
          ((eq? (car lst) '() ) (scan (cdr lst) depth (+ idx 1) best))
          ((pair? (car lst)) (scan (cdr lst) depth (+ idx 1) best))
          ((eq? (car lst) op) (scan (cdr lst) depth (+ idx 1) idx))
          (else (scan (cdr lst) depth (+ idx 1) best))))
  (scan expr 0 0 #f))

(define (split-at lst idx)
  (if (= idx 0)
      (cons '() lst)
      (let ((rec (split-at (cdr lst) (- idx 1))))
        (cons (cons (car lst) (car rec)) (cdr rec)))))

(define (sum? expr)
  (and (pair? expr) (find-rightmost-op '+ expr)))

(define (addend expr)
  (let* ((idx (find-rightmost-op '+ expr))
         (parts (split-at expr idx)))
    (let ((left (car parts)))
      (if (null? (cdr left)) (car left) left))))

(define (augend expr)
  (let* ((idx (find-rightmost-op '+ expr))
         (parts (split-at expr idx)))
    (let ((right (cddr parts)))
      (if (null? (cdr right)) (car right) right))))

(define (product? expr)
  (and (pair? expr)
       (not (find-rightmost-op '+ expr))
       (find-rightmost-op '* expr)))
#+end_src

Part b is considerably more involved. The key insight is that =+= has lower precedence than =*=, so a sum is any expression containing a top-level =+=. We find the rightmost =+= (to ensure left-associative parsing) to split =addend= from =augend=. If no top-level =+= exists but a top-level =*= does, the expression is a product.

** Exercise 64
The following procedure =list->tree= converts an ordered list to a balanced binary search tree. The helper procedure =partial-tree= takes as arguments an integer n and a list of at least n elements and constructs a balanced tree containing the first n elements of the list. The result returned by =partial-tree= is a pair (formed with =cons=) whose =car= is the constructed tree and whose =cdr= is the list of elements not included in the tree.

#+begin_src scheme
(define (list->tree elements)
  (car (partial-tree elements (length elements))))

(define (partial-tree elts n)
  (if (= n 0)
      (cons '() elts)
      (let ((left-size (quotient (- n 1) 2)))
        (let ((left-result (partial-tree elts left-size)))
          (let ((left-tree (car left-result))
                (non-left-elts (cdr left-result))
                (right-size (- n (+ left-size 1))))
            (let ((this-entry (car non-left-elts))
                  (right-result (partial-tree (cdr non-left-elts)
                                              right-size)))
              (let ((right-tree (car right-result))
                    (remaining-elts (cdr right-result)))
                (cons (make-tree this-entry left-tree right-tree)
                      remaining-elts))))))))
#+end_src

a. Write a short paragraph explaining as clearly as you can how =partial-tree= works. Draw the tree produced by =list->tree= for the list =(1 3 5 7 9 11)=.

b. What is the order of growth in the number of steps required by =list->tree= to convert a list of n elements?

*** Solution
Part a: =partial-tree= works by dividing the n elements to be placed into three groups. It allocates ⌊(n-1)/2⌋ elements to the left subtree and the remaining ⌈(n-1)/2⌉ elements to the right subtree, with one element becoming the root. It first recursively builds the left subtree from the front of the list, then takes the next element as the root entry, then recursively builds the right subtree from the remaining elements. Because the input list is sorted and the split is always roughly half-and-half, the resulting tree is balanced.

For =(1 3 5 7 9 11)= the produced tree is:

#+begin_src
        5
       / \
      3   9
     /   / \
    1   7   11
#+end_src

Part b: Each element is visited exactly once — =partial-tree= processes each element in the list by either placing it as a root entry or passing it through the recursive calls. Therefore the order of growth is Θ(n).

** Exercise 65
Use the results of exercises 2.63 and 2.64 to give Θ(n) implementations of =union-set= and =intersection-set= for sets implemented as (balanced) binary trees.

*** Solution
#+begin_src scheme
; Convert both trees to sorted lists, apply the ordered-list
; operations from exercises 2.62 and the intersection analogue,
; then convert the result back to a balanced tree.

(define (union-set-tree set1 set2)
  (list->tree
   (union-set-list (tree->list-2 set1)
                   (tree->list-2 set2))))

(define (intersection-set-tree set1 set2)
  (list->tree
   (intersection-set-list (tree->list-2 set1)
                          (tree->list-2 set2))))

; Where union-set-list and intersection-set-list are the
; Θ(n) ordered-list versions:

(define (union-set-list set1 set2)
  (cond ((null? set1) set2)
        ((null? set2) set1)
        (else
         (let ((x1 (car set1)) (x2 (car set2)))
           (cond ((= x1 x2)  (cons x1 (union-set-list (cdr set1) (cdr set2))))
                 ((< x1 x2)  (cons x1 (union-set-list (cdr set1) set2)))
                 (else        (cons x2 (union-set-list set1 (cdr set2)))))))))

(define (intersection-set-list set1 set2)
  (if (or (null? set1) (null? set2))
      '()
      (let ((x1 (car set1)) (x2 (car set2)))
        (cond ((= x1 x2) (cons x1 (intersection-set-list (cdr set1) (cdr set2))))
              ((< x1 x2) (intersection-set-list (cdr set1) set2))
              (else       (intersection-set-list set1 (cdr set2)))))))
#+end_src

Each step is Θ(n): =tree->list-2= is Θ(n), the ordered-list union and intersection are Θ(n), and =list->tree= is Θ(n). The composition of Θ(n) operations is Θ(n) overall.

** Exercise 66
Implement the =lookup= procedure for the case where the set of records is structured as a binary tree, ordered by the numerical values of the keys.

*** Solution
#+begin_src scheme
(define (lookup given-key tree-of-records)
  (if (null? tree-of-records)
      #f
      (let ((current-key (key (entry tree-of-records))))
        (cond ((= given-key current-key)
               (entry tree-of-records))
              ((< given-key current-key)
               (lookup given-key (left-branch tree-of-records)))
              (else
               (lookup given-key (right-branch tree-of-records)))))))
#+end_src

This is a standard binary search tree lookup. At each node we compare the target key against the current node's key and recurse into the left subtree if the target is smaller, the right subtree if it is larger, or return the record if we have found a match. For a balanced tree of n records this requires Θ(log n) steps, compared to Θ(n) for the unordered or ordered list representations.
